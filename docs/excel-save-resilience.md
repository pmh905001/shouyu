# Excel 保存韧性 & 通知体验 设计文档

> 状态：**方案已确认，待实现**
> 本文用于在动手前对齐存储方案、流程与通知策略。§6、§9 的待讨论点均已拍板。

## 1. 背景与问题

当前痛点（来自你的描述 + 代码走查）：

1. **kb.xlsx 被 Excel/WPS 占用时，保存会失败**，且失败后一段时间内后续的保存也会持续失败——用户唯一的手动补救是关掉 Excel，但关闭+等待重新打开的过程慢、打断心流。
2. **失败提示体验差**：今日任务保存失败时最终会弹一个阻塞式 `QMessageBox`（红色/警告图标），需要等完整的重试链路（约 33 秒）跑完才出现，感知上"卡了好久才告诉我失败"。
3. **截图/剪贴板保存（`Ctrl+Shift+Enter`）路径更脆弱**：这条路径是同步执行、无重试、无兜底文件；一旦保存慢（正比于 workbook 体积，尤其是里面已经嵌了多少张图）就会卡住热键响应，体验上就是"截图之后要等好几秒才弹提示"。
4. **异常退出后数据可能丢失或需要手工找回**：现在如果重试全部耗尽，代码会把整本 workbook 另存为一个 `xxx.unsaved_<时间戳>.xlsx` 兜底文件，但**没有任何代码会在下次启动时去读这个文件**——用户必须自己记得这个文件存在、手动把内容合并回 kb.xlsx。如果是进程被杀 / 崩溃（没走到重试耗尽这一步），连这个兜底文件都不会生成，数据只存在于内存里，直接丢失。

## 2. 现状代码走查（不是重新设计，是先把家底摸清楚）

- **今日任务保存**（`habit_dialog.py::_persist_plan_in_background`）：后台线程跑，`PermissionError`（文件被占用）重试 6 次（间隔 1/2/5/10/15s），重试期间弹一次「重试中」的 `win11toast` 轻提示；全部失败后落盘 `.unsaved_*.xlsx` 兜底文件，再弹阻塞的 `QMessageBox`。
- **剪贴板/截图保存**（`action/shortcut.py` → `excel.py::append()`）：**同步**执行在热键响应线程上，无重试、无兜底文件；失败直接抛异常，被 `@action_handler` 兜底捕获后弹一次性的 `win11toast`（"Failed"）。这条路径比今日任务路径弱很多。
- **通知**其实已经有两种机制在用：
  - `win11toast`（`view/msgbox.py::MessageBox.pop_up_message`）——非阻塞、轻量，目前用于"重试中/已保存/失败"等提示。**这个机制本身没问题，已经是你想要的"快速弹出的泡泡消息"**，问题不在通知技术本身，而在于"要等保存流程跑完才触发通知"。
  - `QMessageBox`（`qt_app.py::show_save_status`）——阻塞式模态框，只用于"重试全部耗尽"这一种终态。
- **备份机制**（`excel.py`）：每次成功写入前都会把当前 kb.xlsx 整份复制一份到同目录下 `xxx_backup_<时间戳>.xlsx`，按 `max_backups` 数量做轮转清理；workbook 损坏时会自动从最近一份能打开的备份恢复。**这个机制是独立的、已经工作良好，新方案不需要动它**，只是需要注意它是"全量拷贝"，文件越大越慢。
- **进程生命周期**：没有 `atexit`/信号处理/看门狗，进程被杀或崩溃时，任何还在内存里、没来得及写盘的东西直接消失。

## 3. 你提出的方案 & 我的评估

你的思路：写 Excel 失败时不再死等/报错，而是先落盘到本地（文本文件 or sqlite3），形成一个"待写入队列"；后台定期重试把队列里的内容合并进 kb.xlsx；Excel 关闭后队列自然会在某次重试时清空。截图单独存文件，队列里只记路径。

这个方向是对的，方向本身就是标准的"本地持久化 outbox 队列 + 后台异步落库"模式。剩下的是选型：**纯文本队列 vs sqlite3。**

### 3.1 纯文本 / JSON Lines 队列文件

| | 说明 |
|---|---|
| 优点 | 实现最简单；人可读，出问题直接用记事本打开看；追加写入本身很快 |
| 缺点 | **"消费后要把已处理的行删掉"这一步天然麻烦**——文件不支持原地删除某一行，只能整份重写（读全部→过滤→写临时文件→原子替换），重写过程如果中途崩溃需要额外兜底；多线程/多次热键触发时的并发追加需要自己加锁；队列变大后没有索引，查"有多少条卡了多久"要整份扫描 |

### 3.2 sqlite3 队列（`pending_writes` 表）

| | 说明 |
|---|---|
| 优点 | Python 标准库自带，不引入新依赖，仍然是"一个本地文件"，不违背"轻量"；**插入即落盘、删除即释放，都是标准事务，不用自己写"重写整个文件"的补偿逻辑**；WAL 模式下多线程读写安全（热键线程插入 + 后台线程消费不会互相踩）；天然支持按状态/时间查询（"还有几条没同步""卡了多久"），后续做"卡太久提醒"很方便 |
| 缺点 | 不能直接拿记事本打开看；调试需要 `sqlite3 pending.db "select * from pending_writes"` 或写一个很小的查看脚本/CLI 参数 |

### 3.3 推荐：**sqlite3**

你最初倾向文本文件，但仔细看你自己列的两个硬性要求——**"异常退出后要能补上"**（崩溃可靠性）和**"排查问题要方便"**——恰恰是文本队列最弱的两块：

- 文本队列的"消费后删除"要靠整份重写，重写这一步本身也可能被异常退出打断，等于给自己新增了一个"重写中崩溃"的边界情况要处理；sqlite 的事务提交/删除是原子的，不需要额外设计。
- 文本队列没有结构化查询，"这条卡了多久""重试了几次"这些信息只能自己在每行里塞字段再手写扫描逻辑；sqlite 用一张表 + 几个字段就有了，而且后续加字段（比如加个 `last_error`）是一条 `ALTER TABLE`，不用改解析逻辑。

调试体验的差距可以用一个很小的补偿动作抹平：加一个 `--show-pending` 命令行参数（或挂在托盘菜单里，"查看待同步队列"），一行 SQL 转成人类可读文本打印出来——成本很低，换来的是崩溃安全性上不需要自己额外设计补偿逻辑。所以综合来看 sqlite3 更适合你列的这几条约束。

> 💬 待讨论 A：如果你已经有其他理由坚持用文本文件（比如想手动 grep/编辑队列内容），告诉我，我可以按文本方案重新设计"重写补偿"这部分，但默认建议走 sqlite3。

## 4. 推荐的整体流程

### 4.1 统一的 `PendingWriteQueue`

现状里"今日任务保存"和"剪贴板/截图保存"是两条独立、强度不一致的路径（前者有重试+兜底，后者几乎没有）。建议把两条路径都收口到同一个队列组件：

```
pending_writes 表（此处为简化版，通用化后的完整设计见 §8.3）：
  id             INTEGER PRIMARY KEY
  created_at     TEXT
  kind           TEXT   -- 'plan_save' | 'clipboard_append'
  payload        TEXT   -- JSON：任务快照 / 剪贴板文本
  attachment_id  INTEGER -- 关联 attachments 表（截图等二进制内容），没有则为 NULL
  status         TEXT   -- 'pending' | 'done' | 'failed'
  attempts       INTEGER
  last_error     TEXT
```

截图这类二进制内容不直接塞进 `pending_writes` 这一行，而是先写进一张独立的 `attachments` 表，`pending_writes` 只存它的 `attachment_id`——这个设计决策（BLOB 内联到 sqlite 还是存成本地文件）单独在 §8.2 讨论。

### 4.2 写入路径（热键 / 保存按钮触发时）

1. 把要保存的数据（任务快照 / 剪贴板文本 / 截图路径）插入一行到 `pending_writes`（`status='pending'`）。这一步很快（几毫秒级），且**跟 kb.xlsx 现在有多大、锁没锁没有任何关系**。
2. 立即弹 `win11toast` 轻提示（"已记录，后台同步中"）——不需要等 Excel 真正写进去。这直接解决"截图后要等好几秒才有反馈"的问题：反馈时机从"Excel 写完"提前到"落盘到队列"。
3. 触发（或唤醒）后台消费线程尝试立即写一次（不用死等下一个定时周期）。

### 4.3 后台消费（drain）线程

- 一个常驻的后台线程，定期（比如每 20-30 秒）+ 每次有新写入时被唤醒，尝试把所有 `status='pending'` 的行按顺序合并写入 kb.xlsx。
- 复用现有 `excel.py` 的 `_atomic_save` / 备份 / `PermissionError` 重试逻辑——这部分不用重新发明，本来就是对的，只是现在"重试完就放弃"的终态行为要改成"这次不行，等下一个消费周期再试"。
- 因为有持久化队列兜底，**不再需要现在这种"1/2/5/10/15 秒连续重试 6 次就报错"的急迫节奏**——可以放宽成"每次消费周期试一次，不行就等下一轮"，Excel 关闭后自然会在某一轮消费成功，全程不需要弹任何阻塞框。
- 成功写入的行标记/删除；失败的行保留、`attempts+1`、记录 `last_error`，继续留在队列里等下一轮。

### 4.4 通知策略调整

| 场景 | 现状 | 建议 |
|---|---|---|
| 正常写入队列 | 无独立反馈（今日任务是后台无声，剪贴板是同步等待） | 立即弹一次 `win11toast`「已记录」，不等 Excel |
| Excel 被占用，消费失败 | 重试链路跑完后弹阻塞 `QMessageBox` | **不弹阻塞框**；如果队列里有条目连续卡超过一个阈值（比如 30 分钟），弹一次「有 N 条还没同步到 Excel，可能是文件被占用」的轻提示，且限频（比如一小时最多提一次），不打断操作 |
| Excel 恢复可写，消费成功 | 弹「重试成功」toast | 保持，`win11toast` 已经够快够轻 |
| kb.xlsx 本身损坏（备份恢复失败等真正不可恢复的错误） | 阻塞 `QMessageBox` | 保留阻塞框——这种情况确实需要用户立刻介入，跟"文件被占用"是不同性质的问题，不应该用同一套提示强度 |

> 💬 待讨论 B：卡住提醒的阈值（30 分钟？1 小时？）和频率你有偏好吗？还是干脆 v1 先不做"卡住提醒"，只保证数据不丢、下次消费自动补上？

### 4.5 崩溃 / 异常退出后的启动恢复

启动流程（`main.py` 的 `_run_daemon`）里现在已经有几个一次性定时器（提醒备份恢复、晨间弹窗、番茄钟），加一步：

- 启动时打开 `pending.db`，如果存在 `status='pending'` 的历史记录（说明上次退出前没消费完，或者进程被杀），立即触发一次消费尝试。
- 只有当尝试后仍然失败、且积压条目数不小（比如 > 0 且已经过了一段时间）时才弹一次提示，否则安静地在后台补上——多数情况下用户根本不会感知到"上次有条目没保存成功"，因为这次启动就自动同步了。

这正好补上你提到的「shouyu 异常退出，这些信息在下次启动时也能正常保存进去」这个要求——现状完全没有这一段逻辑，是本方案里新增、而不是修改的部分。

## 5. 明确不在这次改动范围内的东西

- 备份机制（§2 里的全量拷贝 + 轮转）本身不变，继续复用。
- `kb.xlsx` 因为内嵌图片越来越多导致**单次保存本身越来越慢**（保存耗时正比于 workbook 体积）是一个独立、更大的优化话题（比如截图改成只存本地文件+超链接，而不是内嵌进 xlsx）——本方案通过"把慢操作挪到后台线程"绕开了它对交互体验的影响，但没有解决"后台线程本身跑多久"这个根问题。如果以后 kb.xlsx 变得很大、后台消费经常跑不完一个周期，可以另开一个文档讨论这个。
- 现有的"损坏恢复"（`_recover_from_backup`）和"手动从备份恢复"对话框不变。

## 6. 决策结论

- ✅ A：队列存储用 **sqlite3**。
- ✅ B：**v1 就做**"队列卡住太久"提醒，阈值 **30 分钟**，做成 `kb.ini` 可配置项（`[basic] stuck_alert_minutes=30`，或独立 `[queue]` section——命名不影响功能，实现时随手定），默认 30。提醒频率仍按"之后每小时最多再提一次"处理，避免刷屏。
- ✅ C：截图缓存目录用 **`kb.ini` 同级新建 `pending_images/`**。
- ✅ D：**两条路径都收口**到统一队列——"今日任务保存"和"剪贴板/截图保存"一起走新的 `PendingWriteQueue`。

## 8. 面向未来：从"待写入队列"升级为统一消息队列基础设施

你提出了一个更大的方向：这次做的队列不只是"给 Excel 保存兜底"的临时方案，而是未来**所有数据落地 sqlite 的总入口**——写入先进队列，再由队列分发到各自的目标表；而且队列本身要支持图片之外的二进制内容（pdf/xlsx/zip）和文本文件。这一节专门讨论这个更大的设计，跟 §1-7（这一轮先落地的 Excel 韧性改造）是兼容、但范围更广的关系。

### 8.1 目标澄清

三个诉求叠在一起：

1. **队列是总入口**：任何要保存的东西先进队列（持久化落盘），再被"分发"到各自的最终归宿（今天是 kb.xlsx，以后是某张 sqlite 表）。
2. **队列要支持任意二进制/文本附件**：不只是截图 PNG，还要能装 pdf、xlsx、zip、txt。
3. **数据要方便整体搬迁**：这是你自己提出的两难——"分散文件不好整体搬"vs"全塞 sqlite 不好单独查看"，你也不确定该怎么权衡，让我评估。

### 8.2 附件存储策略：按类型区分，而不是单纯按大小

上一版按"大小阈值"一刀切决定内联/外部存储；你的反馈是**图片直接认定存进 sqlite，其他类型再按大小限制**——这个思路更好，按类型区分比单纯按大小区分更贴近真实场景（截图天然小而且量大，外部大文件天然是"偶发的、体积不定的"，两者的处理逻辑本来就该不一样）。调整后的方案：

**a) 图片（`kind` 相关的截图/剪贴板图片）：始终内联存进 `attachments.data`（sqlite BLOB），不做大小判断。**

理由（沿用上一版对比里 BLOB 内联的优点，但不再需要阈值判断这层复杂度）：
- 截图体量天然小（几十 KB～几 MB），sqlite 内联 BLOB 读写不比文件系统慢；
- 内联能拿到"记录和图片同一个事务写入/删除"的原子性，不会出现"消息写进队列了但图片文件还没落盘"的中间态；
- 日常量最大的就是这一类（每次截图都会产生一条），全部留在同一个 `.db` 文件里，"整体搬迁=复制一个文件"这个诉求对绝大多数数据成立。
- 兜底：万一出现异常巨大的"图片"（比如误粘贴了一个超大 TIFF），加一个硬上限（比如 20MB）超过就退化成外部文件存储，避免单条离群数据把数据库文件顶大——这是安全网，不是常规路径。

**b) 非图片类型（pdf / xlsx / zip / txt 等）：设一个大小上限，上限内内联，超过上限存外部文件。**

具体上限数值你还没定，见下面 💬 待讨论 H。低于上限的走法跟图片一样直接内联，这样只有真正的大文件才会额外产生"外部文件"这个分支，代码/心智负担只在少数情况下才需要考虑。

**c) 外部文件的目录结构：按日期分桶，而不是一个平铺目录。**

你提的"按 `year-month-date` 分文件夹"这个方向是对的，具体考虑：
- Windows/NTFS 本身没有像旧 FAT32 那样 65534 个文件的硬限制，但一个目录下堆几千个文件仍然是真实的实践痛点——Explorer 打开变慢、杀毒软件扫描慢、以后你想"只挑一部分文件拷走"时也不好挑；按日期分桶能直接解决这些问题，你的顾虑是对的，只是"硬限制"这个具体原因不完全准确，但结论不受影响。
- ✅ 分桶粒度：**按天（`YYYY-MM-DD/`）**——非图片大文件预期是偶发的，即使一天只产生 1 个文件、文件夹显得"空"，也换来了部分迁移/拷贝时更细的颗粒度，符合你的原始诉求。
- 文件命名：建议用 `attachments.id`（sqlite 里的自增主键，天然唯一）做前缀，再拼上原始文件名，例如 `attachments/2026-08-01/00001234_报表.xlsx`——前缀保证不会因为原始文件名重复/含特殊字符而冲突，后面保留原始文件名是为了双击打开时图标/默认程序识别正确，且人眼一看就知道是什么文件，兼顾"防冲突"和"排查方便"两个目标。

### 8.3 表结构设计

表名按你的建议改叫 `queue`（`queue` 不是 SQLite 的保留字，可以直接用）。几个你提到的细节逐一落实：

**时间戳类型**：SQLite 没有真正的 `DATETIME` 存储类型——声明成 `DATETIME` 只是让这一列获得 NUMERIC 类型近似（会尝试转成数字），并不会得到一个"日期时间"类型本身。SQLite 官方推荐的两种做法是 `TEXT`（ISO-8601 字符串，如 `2026-08-01T09:30:00.123Z`）或 `INTEGER`（Unix 时间戳）。考虑到"排查问题方便"是你反复强调的优先级，建议用 **`TEXT`，ISO-8601、统一存 UTC**：
- 人眼直接可读（`sqlite3 shouyu.db "select * from queue"` 直接能看懂时间），不需要转换脚本；
- ISO-8601 格式按字符串排序等价于按时间排序，索引、`ORDER BY`、`WHERE created_at < ?` 全部直接可用，不会因为"看起来像文本就不能排序"而丢失查询能力；
- 统一用 UTC 存、只在展示（toast 提示、debug 工具输出）时转本地时区——避免"30 分钟卡住阈值"这类判断因为混用本地时间/UTC 出现夏令时或跨时区的隐蔽 bug（虽然你大概率不会跨时区用这个工具，但存储层统一按 UTC 是零成本的好习惯）。

**索引**：核心查询模式是"某状态的、按 id/时间排序的一批" + "卡住超过 N 分钟的" + "所属 kind 是什么"，建一个 `(status, created_at)` 复合索引就能覆盖，索引不必也不该按 `id` 单独建（`INTEGER PRIMARY KEY` 本身就是 ROWID，天然有索引效果）。

**payload 到底是不是 JSON**：不用为"有的 kind 是纯文本、有的是结构化数据"这件事在表里加第二个列或者分支处理——**统一约定 payload 永远是合法 JSON**，纯文本这种情况就是"值恰好是一个 JSON 字符串"（`json.dumps("剪贴板里的一段文字")` 结果就是 `"剪贴板里的一段文字"`，本身就是一段合法 JSON），结构化数据（比如今日任务快照）就是 JSON 对象/数组。读写这一层永远走 `json.dumps`/`json.loads`，dispatcher 拿到反序列化后的 Python 值（str / dict / list）自己按 `kind` 决定怎么解释，队列这一层完全不需要关心、也不需要分支。可以再加一条 `CHECK(json_valid(payload))` 约束（SQLite 自带 JSON1 扩展，`json_valid`/`json_extract` 都能用），插入格式错误的 payload 会直接在写入时报错，而不是等消费的时候才发现——这也顺手打开了"用 SQL 直接查 payload 内容"的调试手段，比如 `select json_extract(payload,'$.text') from queue`，不需要先导出到 Python 里解析。

**最终表结构：**

```sql
CREATE TABLE queue (
  id             INTEGER PRIMARY KEY,             -- 自增，天然的写入顺序/FIFO 位置
  created_at     TEXT NOT NULL,                   -- ISO-8601 UTC
  updated_at     TEXT NOT NULL,                   -- 每次状态变化时更新
  kind           TEXT NOT NULL,                   -- 'plan_save' | 'clipboard_append' | 未来新增
  payload        TEXT NOT NULL CHECK(json_valid(payload)),
  attachment_id  INTEGER REFERENCES attachments(id),
  status         TEXT NOT NULL DEFAULT 'pending',  -- 'pending' | 'processing' | 'done' | 'dead'
  attempts       INTEGER NOT NULL DEFAULT 0,
  claimed_at     TEXT,                             -- 消费线程"领走"的时间，检测卡死用（见 §8.5）
  last_error     TEXT
);
CREATE INDEX idx_queue_status_created ON queue(status, created_at);

-- attachments（二进制/文本内容的统一存放点，见 §8.2）
```

新增一种 `kind`，只是"多加一个 dispatcher 函数"，不需要改表结构——这就是"通用化"真正省下来的成本：现在只需要写 2 个 dispatcher（`plan_save` → 写 kb.xlsx，`clipboard_append` → 写 kb.xlsx 的另一个位置），以后每加一种要保存的东西，加一个 dispatcher 函数就行，队列本身、通知逻辑、崩溃恢复逻辑全部不用碰。

**一个值得现在就想清楚的洞察："分发"这一步的正确性，取决于目标表和队列是不是在同一个 sqlite 文件里。**

- 现在的场景（分发目标是 kb.xlsx）：队列（sqlite）和目标（openpyxl 写的 xlsx 文件）是两个不同的系统，没法把"写 Excel"和"标记这条消息为 done"放进同一个事务——所以只能靠 §4.3 的"重试 + 保留 attempts"来保证"万一中间失败也不会丢，顶多重复尝试"。
- 以后的场景（分发目标是某张 sqlite 表）：**如果这张目标表和 `queue` 在同一个数据库文件里**，"写入目标表" + "把这条消息标记为 done / 推进游标"可以包在同一个 `BEGIN...COMMIT` 事务里，两件事要么一起成功要么一起失败，天然不会出现"重复写入目标表"或"消息标记完成了但目标表没写"的问题——不需要额外设计幂等键之类的补偿逻辑。这是"以后所有数据都放 sqlite"这个大方向本身带来的免费正确性收益，也是我建议**队列表和未来所有的领域表放进同一个 `.db` 文件**（而不是队列单独一个 `queue.db`，业务数据另一个 `data.db`）的核心原因——不只是为了搬迁方便，更是为了让"分发"这个动作可以做到原子。

### 8.4 消费模型：流水账 + 游标，而不是"处理完就删除"

上一版隐含的模型是"处理成功就删除/标记 done，成功的记录逐渐从表里消失"。你提到想做成**流水账**——每一条写入过的记录都留着，读取"处理到哪了"靠一个类似指针的东西，删历史数据只在手工触发时才发生。这个思路本身是个成熟模式（很像 Kafka 的 log + consumer offset，或者 WAL），而且跟这份文档一直在强调的"崩溃后要能补、排查要方便"天然契合——历史记录留着，任何时候想查"上周三这个时间点到底保存了什么"都能直接查到，比"处理完就删掉，出问题只能两眼一黑"强得多。具体设计：

```sql
CREATE TABLE queue_cursor (
  consumer    TEXT PRIMARY KEY,   -- 'excel_dispatch'，以后可以有多个独立消费者
  last_id     INTEGER NOT NULL DEFAULT 0,
  updated_at  TEXT NOT NULL
);
```

- **消费不再删除行**，只是把 `queue.status` 改成 `'done'`（或失败到底后改成 `'dead'`，见 §8.5），行本身永久留在表里。
- **游标（`queue_cursor.last_id`）记录"连续处理完的最高位置"**：消费线程从 `last_id + 1` 开始按 `id` 顺序扫描，只要遇到的行状态是 `'done'` 或 `'dead'`（两者都算"已解决，不再挡路"）就把游标往前推；一旦遇到 `'pending'`/`'processing'` 就停在那——这样"当前处理到哪"是一个 O(1) 的单值读取（`SELECT last_id FROM queue_cursor WHERE consumer=?`），不需要每次都扫整张表去猜。
- 因为消费者是按 `consumer` 字段区分的，**以后如果想加一个完全独立的"消费者"**（比如以后做一个全文检索索引器，从头把这条流水账再读一遍建索引，跟"分发到 Excel"这个消费者互不干扰、各自维护自己的进度），只需要插一行新的 `queue_cursor`，不需要改 `queue` 表本身——这跟 §8.3 说的"新增 kind 只需要加 dispatcher 函数"是同一个"通用化省成本"的道理，游标机制额外把它扩展到了"未来可能不止一个消费者"这个场景。
- ✅ **手工清理**（"较早的历史数据"）：**整行删除**——只动 `status IN ('done', 'dead')` 且早于某个时间的行（连同 `attachment_id` 指向的图片/文件一起清掉），永远不动 `pending`/`processing`。代价是清理掉的部分不再能查"那天做过什么"，但实现更简单，且反正是手工触发、你自己决定什么时候清、清多老的数据，不会有意外丢失。

### 8.5 卡死 / 坏消息的处理（dead-letter）

单机单消费者场景不需要分布式消息队列那些复杂机制（多消费者协调、分区之类），但两个问题仍然值得在表结构里提前留好位置：

- **消费线程处理到一半崩了怎么办**：给 `status` 加一个 `'processing'` 中间态 + `claimed_at` 时间戳，消费线程领走一条消息时标记 `processing` 并记下时间；如果重启后发现某条 `processing` 的消息 `claimed_at` 是很久以前（比如超过 5 分钟，正常处理不该这么久），说明上次处理到一半就崩了，直接安全地重置回 `pending` 再试一次即可（因为 §8.3 说的"同库事务"保证了"重试一条已经处理过的消息"不会造成重复写入）。
- **一条消息本身有问题，一直处理失败**（比如 payload 格式错了，不是"Excel 被占用"这种会自愈的失败）：不应该让它一直挡在队列前面、拖累后面所有正常消息的消费。建议 `attempts` 超过一个上限（比如 10 次）后标记为 `'dead'`，§8.4 的游标推进规则里 `'dead'` 跟 `'done'` 一样"算已解决"，游标会跳过它继续往前走，不会卡住后面的消息；`dead` 消息通过 §7 提到的"查看队列"工具单独暴露出来，需要人工看一眼，但不阻塞整体流程。

这两点现在可以先只是"预留字段"（`processing`/`dead` 状态、`claimed_at` 列），具体的检测/清理逻辑可以等真正遇到（或者在这轮实现里顺手写一个最简单版本）——表结构留好比逻辑更重要，因为表结构改起来成本更高。

### 8.7 几个纯实现细节（不需要你拍板，写出来是为了透明）

以下几点属于"任何合理实现都会这么做"的技术细节，我会直接按这个来写，除非你有不同意见，否则不单独占用你的决策精力：

- **并发访问方式**：不用自己维护一个进程内的锁/单例连接，改成"每次操作开一个短生命周期的连接，打开 WAL 模式 + 设置 `busy_timeout`（比如 5000ms）"——这是 sqlite 官方推荐的多线程访问方式，写冲突时 sqlite 自己重试等待，而不是抛 `database is locked` 让业务代码处理。热键线程写入队列、后台消费线程读取/更新，都走这一套，互不需要显式协调。
- **WAL 文件增长/checkpoint**：sqlite 默认会在 WAL 文件涨到一定大小时自动 checkpoint，对这种个人工具级别的写入量（一天几十到几百次操作）完全够用，不需要手动管理。
- **是否要 `VACUUM`**：`DELETE`/清空 BLOB 之后 sqlite 不会自动收缩文件体积，但因为 §8.4 的清理是手工触发的低频操作，可以在同一个"手工清理"动作里顺手带一次 `VACUUM`（或增量式的 `PRAGMA incremental_vacuum`），不需要单独设计一套自动收缩机制。
