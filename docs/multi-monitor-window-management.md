# 多屏窗口管理：一键跨屏 + 断连自动还原

> 状态：**调研 + 方案讨论（未开始实现）**

## 1. 背景

你的实际布局：笔记本 + 2 台外接屏，呈"倒品"字形——上面两个外接屏并排，下面是笔记本自己的屏幕。两个具体痛点：

1. **手动拉宽很烦**：用 VS Code 看很多信息、用 Excel/DBeaver 看很多表格时，都需要把窗口手动拖到跨越上面两块屏——每次都要重新拖一遍。
2. **开会回来对不上**：带笔记本去会议室（只剩 1 块屏），回工位后（恢复 3 块屏），之前跨两屏的窗口不会自动回到原来的样子，还要再手动拖一遍。

这两个问题本质是同一类底层能力（识别屏幕、挪窗口）支撑的两个不同场景：**①主动触发**（热键让当前窗口跨屏）、**②被动恢复**（拓扑变化后自动把窗口放回原位）。

## 2. 技术可行性验证

用你现有的 `pywin32`（已经是项目依赖）在你这台机器上实测跑通了这几个关键 API：

```python
win32api.EnumDisplayMonitors()      # 拿到所有显示器
win32api.GetMonitorInfo(hMonitor)   # 每个显示器的坐标范围 + 是否为主屏
win32gui.GetForegroundWindow()      # 当前聚焦的窗口
win32gui.GetWindowRect(hwnd)        # 窗口当前位置/大小
win32gui.SetWindowPos(hwnd, ...)    # 挪动 + 拉伸窗口
win32process.GetWindowThreadProcessId(hwnd)  # 反查窗口所属进程（配合 psutil 拿进程名）
```

这些都是标准、成熟的 Win32 API，`move_column`/热键这些功能已经在用同一套 pywin32，技术路线上没有新增依赖，风险主要在"你实际三屏环境下的坐标细节"，这个我这边验证不到（沙盒里只有 2 块虚拟屏），需要你实机测。

**一个必须处理的坑：DPI 缩放。** 如果 shouyu 进程本身没有声明"每显示器 DPI 感知"，Windows 会在不同缩放比例的屏幕之间对坐标做虚拟化转换，导致 `SetWindowPos` 算出来的坐标跟实际物理像素对不上（外接屏和笔记本屏缩放比例不一致时最容易出问题）。需要在启动时加一行 `ctypes.windll.shcore.SetProcessDpiAwareness(2)`（PROCESS_PER_MONITOR_DPI_AWARE）声明清楚，这个已经在方案里考虑了。

## 3. 功能一：热键一键跨屏

### 3.1 怎么"认出"是哪几块屏

三种识别方式，各有取舍：

| 方式 | 说明 | 稳定性 |
|---|---|---|
| **按位置**（"最上面一排"/"最下面一排"/"最左边一列"）| 按 `Monitor` 矩形的 top/left 排序分组 | 只要你在 Windows 显示设置里没有反复重新排列屏幕，位置关系很稳定；重新插拔一般不会打乱物理摆放 |
| **按分辨率**（如 `1280x800` 专指笔记本屏）| 跟 pomodoro 悬浮窗那个修复用的是同一个思路 | 前提是各屏分辨率不同，重合的话没法区分左右 |
| **按显示器索引/设备名**（`\\.\DISPLAY1`）| Windows 分配的设备名 | ❌ 不推荐，重新插拔后设备名/顺序完全可能变 |

你的场景正好可以把两种方式配合起来用：**"上面两块"用位置识别**（因为是并排的两块，位置关系天然稳定），**"笔记本屏"用分辨率识别**（因为笔记本屏分辨率通常跟外接屏不一样，且这个特征不随插拔变化）。

### 3.2 热键触发时具体做什么

```
1. 拿到当前聚焦窗口 hwnd = GetForegroundWindow()
2. 如果窗口当前是最大化状态，先还原（SetWindowPos 对最大化窗口不生效）
3. 解析目标区域（比如"上面两块屏"）→ 算出这几块屏 Work 区域的并集矩形
4. SetWindowPos(hwnd, 目标矩形) —— 一步到位跨屏铺满
```

不需要关心"这个窗口是 VS Code 还是 Excel"——热键只是对"当前聚焦的窗口"生效，通用、简单，跟你实际用法（先点一下想调整的窗口，再按热键）完全匹配。

### 3.3 配置形式（草案）

```ini
[window_snap]
;命名一个区域：position:top2 = 最上面的两块屏（按 top 坐标分组取最小的一组，
;组内再按 left 排序拼成横向并集）；resolution:1280x800 = 指定分辨率的那块屏。
region_office_wide=position:top2
region_laptop_only=resolution:1280x800

;把区域绑定到热键。
snap_office_wide=ctrl+alt+up
snap_laptop_only=ctrl+alt+down
```

> 💬 待讨论 A：区域定义语法你觉得这样直观吗？还是想要更简单的形式（比如干脆固定成"snap_top_two"/"snap_bottom_one"两个内置热键，不做成通用配置）？给你两个方向都行，通用配置更灵活，内置热键更省心。

## 4. 功能二：断连后自动还原

### 4.1 核心机制：记住"这个拓扑下，这个 App 该在哪"

思路：**不需要你显式"保存布局"这个动作**——每次你用功能一的热键把某个窗口拖到某个区域时，顺手记一笔：

```
(当前屏幕拓扑签名, 该窗口所属进程名) -> 刚刚设置的矩形
```

存进 `shouyu_state.json`（复用你已有的 `AppState`，这类"学到的动态状态"本来就该放这里，不是放 kb.ini 那种静态配置）。

之后**后台一个每隔几秒检查一次屏幕拓扑的线程**（比较 `EnumDisplayMonitors()` 拿到的屏幕数量+尺寸组合，算一个"拓扑签名"）——一旦检测到拓扑从"当前"变回"某个之前见过、且有记录的签名"（比如从"1 块屏"变回"3 块屏"），就自动把有记录的那些进程（按进程名找它们当前的窗口，`EnumWindows` + `GetWindowThreadProcessId` + `psutil` 拿进程名比对）用 `SetWindowPos` 摆回记住的矩形——前提是那个进程当时确实开着（没开就什么都不做）。

这样"开会回来"这个场景就是：你去开会前用过的布局已经被记住了，回来后拓扑一变回原样，后台线程自动把 VS Code/Excel 摆回原位，不需要你做任何操作。

### 4.2 拓扑签名怎么定义

建议用"屏幕数量 + 每块屏的(宽,高,left,top)排序后的元组"整体做签名——足够区分"3 屏品字形" vs "1 屏会议室" vs 万一将来接了个投影仪之类的第三种情况，不需要你显式给拓扑起名字（不用配置"办公室模式"/"会议室模式"这种），纯粹是"见过这个组合 → 有没有存过东西 → 有就还原"。

> 💬 待讨论 B：这套"自动检测 + 自动还原"你想要一直在后台跑（默认行为），还是想要一个开关（比如怕万一误判乱挪窗口，想要能关掉/只在手动触发时生效）？我倾向默认开启但可关闭，因为触发条件（拓扑变化且有历史记录）本身已经很保守，误判概率低。

### 4.3 检测节奏

轮询 `EnumDisplayMonitors()` 的开销很小（毫秒级），建议每 3-5 秒查一次，不会有性能问题。也调研了另一种方式——监听 Windows 的 `WM_DISPLAYCHANGE` 消息（显示器配置变化时系统会广播这个消息），理论上更"实时"（不用等轮询周期），但需要一个能收 Windows 消息的窗口句柄去挂钩子，shouyu 目前的后台进程主要靠 pystray 托盘 + 隐藏的 Qt 窗口，接消息需要额外包一层——轮询方案实现更简单、足够快（几秒钟的延迟对"开会回来"这个场景完全无感），除非你特别在意"最快能有多快"，我更推荐轮询。
