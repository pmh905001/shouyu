## 文件夹规则

| 规则 | 说明 |
|---|---|
| 只分一层 | `requirements/` 和 `design/` 下面按模块分子文件夹，子文件夹里不再分文件夹 |
| 按模块分，不按里程碑分 | 模块是稳定的，里程碑的划分可能调整。某个里程碑有哪些文档，看路线图 |
| 需求总表 | 每个模块文件夹里的 `20261030-01-*.md` 是这个模块的需求总表，列出全部需求编号、优先级、验收标准和现状 |
| 细化文档 | 细化某个里程碑时，在对应模块文件夹里新建一篇细化文档，总表里对应的需求链接过去 |
| 新模块 | 现有模块放不下时再新建子文件夹，比如 M5 的任务和番茄放在 `planning/` |

## 文件命名

`requirements/` 和 `design/` 下的文档统一命名为 `<年月日>-<序号>-<主题>.md`，例如 `20261030-01-overview.md`。

| 部分 | 规则 |
|---|---|
| 年月日 | 文档的创建日期，格式 `YYYYMMDD`。文档以后修改时不改文件名，修改日期写在文档开头的"更新"里 |
| 序号 | 同一个文件夹里、同一天创建的多篇文档，按阅读顺序编号：`01`、`02`……；`99` 留给待确认问题 |
| 主题 | 英文小写，单词之间用 `-` 连接 |

以后新增文档时，用新增那天的日期，比如 `capture/20261105-01-clipboard-to-v2.md`，不用改已有文档的文件名。

`roadmap.md` 和各个 `README.md` 是一直在更新的索引，不加日期前缀。

## 实现状态标记

需求总表里的"现状"一列：

| 标记 | 含义 |
|---|---|
| 已实现 | 现有代码已经满足验收标准 |
| 部分实现 | 有相关的功能，但没有满足全部验收标准；后面写明缺什么 |
| 未实现 | 还没有相关的功能 |
| 待定 | 需求本身还没确定，取决于某个待确认问题 |

注意：

- 现状是对照 v2 分支的代码判断的。目前 v2 分支的代码就是 v1 的代码（起点 `ba6c474`），所以"已实现"指的是 v1 已经实现。v2 换了存储方式后，这些功能大多还要迁移，进度记在 [v1 功能继承清单](requirements/overview/20261030-02-v1-inheritance.md) 的"v2 现状"一列。
- 每完成一个里程碑，就更新相关需求的现状。

## 写作约定

1. **需求和设计分开写。**
   - 需求文档只回答：要解决什么问题、在什么场景下、期望什么结果、怎么判断做到了。
   - 需求文档里不出现表名、字段、库、协议、算法等实现内容。"现状"一列为了说明依据，可以写代码文件名。
   - 设计文档回答怎么做，每个设计决策都要注明对应的需求编号。
2. **先定需求，再做设计。**每个里程碑的流程见 [路线图](roadmap.md) 第 2 节。需求有改动时，先改需求文档，再改设计。
3. **需求编号**：`<模块>-<序号>`，比如 `CAP-04`。编号一旦分配就不再复用，废弃的需求标注"已废弃"，不要删除。
4. **需求来源**：每条需求注明来源。
   - `用户`：用户明确提出的。
   - `建议`：整理过程中补充的，需要用户确认后才算数。
5. **优先级**：
   - `P0`：v2 第一个可用版本必须有。
   - `P1`：应该有，可以晚一些。
   - `P2`：有更好，可以放到以后。
6. **文档状态**写在每篇文档开头：草稿、评审中、已定稿。
