## 文件命名

`requirements/` 和 `design/` 下的文档统一命名为 `<年月日>-<序号>-<主题>.md`，例如 `20261030-01-overview.md`。

| 部分 | 规则 |
|---|---|
| 年月日 | 文档的创建日期，格式 `YYYYMMDD`。文档以后修改时不改文件名，修改日期写在文档开头的"更新"里 |
| 序号 | 同一天创建的多篇文档按阅读顺序编号：`01`、`02`……；`99` 留给待确认问题 |
| 主题 | 英文小写，单词之间用 `-` 连接 |

以后新增文档时，用新增那天的日期，比如 `20261115-01-mobile-view.md`，不用改已有文档的文件名。

## 写作约定

1. **需求和设计分开写。**
   - 需求文档只回答：要解决什么问题、在什么场景下、期望什么结果、怎么判断做到了。
   - 需求文档里不出现表名、字段、库、协议、算法等实现内容。
   - 设计文档回答怎么做，每个设计决策都要注明对应的需求编号。
2. **先定需求，再做设计。**流程是：需求草稿 → 评审 → 定稿 → 设计 → 实现。需求有改动时，先改需求文档，再改设计。
3. **需求编号**：`<模块>-<序号>`，比如 `CAP-04`。编号一旦分配就不再复用，废弃的需求标注"已废弃"，不要删除。
4. **需求来源**：每条需求注明来源。
   - `用户`：用户明确提出的。
   - `建议`：整理过程中补充的，需要用户确认后才算数。
5. **优先级**：
   - `P0`：v2 第一个可用版本必须有。
   - `P1`：应该有，可以晚一些。
   - `P2`：有更好，可以放到以后。
6. **文档状态**写在每篇文档开头：草稿、评审中、已定稿。
